GitHub Copilot Lab

From ticket to pull request

Two hours, one repo, one ticket. You work with GitHub Copilot Chat in VS Code from a Jira-style ticket to a reviewed pull request in a small sales data warehouse (Oracle source, SQL layers, Python orchestration, Power BI), then tune the setup so the next ticket goes faster.

The repo

az-copilot-backend-lab-2026-10 in one picture

A synthetic sales warehouse. Oracle is simulated with SQLite files, the SQL is written Oracle-style. Nothing needs a server or a network.

src (simulated Oracle: products, customers, orders)
  -> stg   raw copy + load timestamp
  -> core  cleaned, conformed (credit-blocked customers and discontinued products stop here)

Look at any table: uv run dwh peek mart.fact_orders
Tickets: DWH-101 status report (Part 1) | DWH-102 credit check (Part 2) | DWH-103 data quality check (Follow-up A)

Setup

Before you start

Check this before 13:00, so the first ten minutes go into the lab and not into setup. If something is missing, ask a facilitator.

Where the controls are, as a schematic of the chat input:

No uv on your machine? Use the dev container

The repo contains a dev container. Install Docker and the VS Code extension Dev Containers, open the repo folder and run Dev Containers: Reopen in Container from the Command Palette. It builds an image with Python 3.13, uv and the Copilot extensions and seeds the demo data, so every command in this lab works unchanged in its terminal. Sign in to Copilot inside the container and check the session target as in the checklist. The first build needs network access and a few minutes, so do it before 13:00.

For facilitators: what the fork must contain
  • The repo is the az-copilot-backend-lab-2026-10 package: tickets/ (DWH-101 to DWH-103), docs/confluence/, powerbi/model.md, .agents/skills/.
  • Participants without uv use the dev container (Docker and the Dev Containers extension required). Build it once beforehand on a clean machine and test Copilot Chat inside it. The dev container is untested here.
  • uv sync works on the workshop network. Run it once beforehand on a fresh clone, uv downloads Python 3.13 and the dependencies.
  • uv run scripts/lab_check.py is red and uv run pytest is green on a fresh fork.
  • AGENTS.md is deliberately thin. If the fork carries an agent-specific instruction file, move its content here.
  • VS Code setting chat.useAgentsMdFile is on for the Local agent.
  • Reference solutions are in solutions/ (DWH-101, DWH-103). AGENTS.md tells the agent not to use them. If you want to be sure, delete the folder in the participant fork.
Part 1 | 65 minutes (13:00 to 14:05)

Ticket to pull request

Walk the whole loop once, the way you would on a real backend ticket. The prompts are one way to say it, reword them. Talk to your neighbor whenever you want to compare.

  1. 1See the “before”, then branch off8 min | baseline

    Open your fork in VS Code. In the integrated terminal create the simulated source data and a demo run history, then look at what the BI team sees every morning today:

    uv run dwh seed
uv run dwh status

    A raw dump of the log table, nine lines. Somewhere in there a step failed. Now run the finish-line check, then read the ticket tickets/DWH-101.md yourself and create your branch:

    uv run scripts/lab_check.py
git switch -c feature/DWH-101-status-report

    You should see: Red. Four [FAIL] lines, one per acceptance criterion the status output misses. You run the same check at the end.

    Tip: In the next steps you attach the ticket to your messages with # and the file name. The pipeline is simulated: Oracle is a set of SQLite files, nothing needs a server.

  2. 2Look at the app7 min | what you are working on

    Before you change anything, see what the pipeline produces. Run it once for real, look at a few rows and open the simulated Power BI report:

    uv run dwh run
uv run dwh peek src.orders
uv run dwh peek mart.fact_orders
uv run scripts/render_report.py

    Open exports/report.html in your browser (Explorer: right-click the file, Reveal in Finder or Reveal in File Explorer). In the dev container the repo folder is shared with your machine, so the file is on your disk as well. Then skim powerbi/model.md: that is how the report would read the mart tables.

    You should see: Raw orders in src, cleaned facts in mart (fewer rows: unshipped orders, credit-blocked customers and discontinued products are filtered out), and a report with orders, revenue and revenue per week. The report is a simulation: no Power BI, no DAX engine.

    Tip: uv run dwh status now shows your live run. The demo run with the failure is still what the check and the ticket use.

  3. 3Explore: follow the data5 min | Ask mode

    Do not guess where the status text comes from. Ask with the whole codebase as context, still in Ask mode:

    Prompt

    #codebase How does `uv run dwh status` get its data, from the log table through the Python code to the console output? Point me at the exact functions and files, and tell me which Confluence page in docs/ defines what "late" means.

    You should see: main in cli.py, render_status and latest_run_rows in status.py, the table ctl.dwh_control in seed.py, and docs/confluence/pipeline-operations.md. Open the References under the answer and check the files are real.

  4. 4Grill the ticket8 min | before anything is planned

    Tickets are rarely finished, even with acceptance criteria. The skill grill-me interviews you in rounds, recommends an answer for each question, and looks up facts in the repo itself. It only runs when you call it. Type / to check it is listed (/skills shows all), then start in Ask mode:

    Prompt

    /grill-me Grill me on #file:tickets/DWH-101.md before we plan anything.

    Answer the first round. Accept the recommendation where it is sensible and challenge at least one. Continue until nothing is left open, then capture the result:

    Prompt

    Append a section "Decisions" to tickets/DWH-101.md with every decision we made, one line each.

    You should see: The lateness rules answered from docs/confluence/pipeline-operations.md instead of asked (a step at exactly 06:00:00, a step at 06:00:30, skipped steps), plus real decisions: does a late step count as OK in "n of total" (the example says 7 of 9), how are steps sorted inside a group, what does the report say when no run exists. If the agent asks you something the page answers, point it there.

    Tip: Compare with your neighbor: which decisions did you make differently? Skip the skill for a one-line fix, use it whenever a ticket hides decisions.

  5. 5Plan: decide first, then push back12 min | Plan agent

    Switch the agent picker from Ask to Plan (or start with /plan). The plan agent proposes and asks questions, it does not edit files.

    Prompt

    Plan the work for #file:tickets/DWH-101.md including its Decisions section. The change belongs in src/dwhpulse/status.py only, no new columns, no SQL change. Cover every acceptance criterion. Do not write code.

    Answer its questions, then push on the technical risks before you approve:

    Prompt

    Before I approve: what could go wrong technically? How do you compute the minutes after 06:00, where does the 06:00 come from, and what do you show for a step that finishes at exactly 06:00:00 and one at 06:00:30? How is the output kept stable? Which tests prove the failed, the skipped and the late case?

    Use Open in Editor to read the plan as a document. When it survives your questions, approve with Start Implementation.

    You should see: A revised plan with the deadline from config.py instead of a magic number, sorted output, a skipped line that names the upstream step, and a test per criterion.

  6. 6Implement: let the agent edit7 min | Agent mode

    Start Implementation switches to the Agent. It edits files and may ask to run terminal commands: read each command before you click Allow. Then look at what it changed in the Source Control view, file by file.

    Prompt

    List every file you changed and explain each change in one line. Did you touch anything outside the plan?

    Tip: Accountability is the point. The agent wrote it, you ship it. Edits you do not like: Undo in the chat or Restore Checkpoint. Checkpoints do not replace git.

  7. 7Verify: check, tests and your own eyes10 min | proof, not trust

    Run the check from step 1, now expecting green. If it is still red, hand the output back with #terminalSelection:

    uv run scripts/lab_check.py
    Prompt

    #terminalSelection The lab check is still failing with this output. Fix it and tell me which acceptance criterion it relates to.

    Then lock the criteria in with tests. The repo already has tests/test_status.py:

    Prompt

    Look at tests/test_status.py and tests/conftest.py. Add tests for the acceptance criteria of #file:tickets/DWH-101.md: summary line, failed first, skipped names its upstream step, late with minutes, stable output. Run uv run pytest and show me the result.

    Finally simulate a fresh failure and read the report as the BI team lead would (a live run uses a simulated scheduler clock starting at 05:00, so nothing is late):

    uv run dwh run --inject-failure core_orders
uv run dwh status

    You should see: [DONE] DWH-101 complete!, new tests that would fail for the raw dump, and a report where the failed step comes first and the skipped step names its cause.

  8. 8Review, commit and pull request8 min | done means reviewable

    Review first: in Source Control hover over Changes and click Copilot Code Review (Free plan: select the code, right-click, Generate Code, Review). Fallback prompt for Agent mode:

    Fallback prompt

    Review my uncommitted changes as a strict senior data engineer. Focus on correctness, edge cases (no run in the log, a run without failures), naming, the conventions in docs/confluence/pipeline-operations.md and anything the ticket did not ask for. Be concise and rank findings by severity.

    What a good review finds here (look after you tried)
    • Deadline boundaries: 06:00:00 must be on time, 06:00:30 must be 1 min late. Rounding down or using “at or after” breaks one of them.
    • Magic number: 06:00 written into status.py instead of read from config.DAILY_DEADLINE.
    • Empty and clean cases: no run in the log, and a run without failures, both still give a sensible first line.
    • Skipped is not late: a skipped step that finished after 06:00 must not appear as LATE.
    • Scope: changes outside status.py and its tests that the ticket did not ask for.

    Decide per finding: fix, or argue why not. Then commit with the ticket key (the sparkle icon drafts a message) and open the pull request from the GitHub Pull Requests view, target your own fork, draft is fine:

    DWH-101 Make the pipeline status readable for the BI team

    You should see: A PR in your fork with DWH-101 in the title, the check result in the description, and a diff limited to the agreed files. Paste the link in the facilitator channel.

Note: You tested after implementing here. Follow-up A turns this around with the test-driven-development skill: tests first, then code. Try both and compare which result you trust more.

Finished early? Pick one
  • Model comparison: on a scratch branch, run the plan prompt of step 5 once with a lightweight model and once with a top-tier model (new chat each, model picker in the chat input, hover a response to see who answered). Which plan raised the edge cases on its own? Was it worth the extra credits?
  • Context meter: the context window control is the small ring at the bottom right of the chat input, in the row with Local and Default permissions. Hover over it for the token count, a breakdown by category and the AI credits of the session. Send one #codebase question, hover again, then run /compact (or select the control and choose Compact Conversation). /context is not a meter: it just makes the agent describe the workspace. If you cannot find the ring, skip it, /compact works without it. A chat that only explores is a throwaway chat.
  • Debugging skill: when the check stays red and the agent starts guessing, call /systematic-debugging.
  • Own ticket: write a ticket with acceptance criteria for a duration column in the status report and run the loop without the guide. Mind the convention: a mart change also updates powerbi/model.md.
Part 2 | 30 minutes (14:05 to 14:35)

Instructions and your first skill

Move what you just learned out of your head and into the repo, so every next session starts smarter.

  1. 1Let Copilot draft instructions, then edit them8 min

    AGENTS.md is deliberately thin. A good one makes every future prompt sharper. In a new Local Agent chat run /init, then merge the draft with the existing file. What belongs in: how to run and test, the architecture in one paragraph, the conventions you noticed in Part 1, no-go areas. Long documentation does not, link to it.

    /init
    Prompt

    Based on what you learned working on DWH-101, improve AGENTS.md. Describe the layers (SRC, STG, CORE, MART, CTL), how to run the pipeline, the tests and the check, and the conventions from docs/confluence/pipeline-operations.md and tests/test_sql_conventions.py (no SELECT *, every SQL file registered in pipeline.py, SRC read only, a mart change updates powerbi/model.md). Keep it under 40 lines.

    You should see: Short and specific. Prove it is used: in a new chat ask how to run the pipeline with a simulated Oracle error and look for AGENTS.md in the References.

  2. 2Write your first skill: ticket-to-spec14 min

    A skill is a folder with a SKILL.md that teaches the agent a procedure, loaded only when its description matches the task. Read tickets/DWH-102.md and skim the two pages it links (docs/confluence/): the ticket is vague on purpose. Then type /create-skill and describe what you want, or create .agents/skills/ticket-to-spec/SKILL.md by hand.

    Requirements: name equals the folder name, lowercase with hyphens. The description is the trigger: say when to use it, not only what it does. Numbered steps, at least one gotcha, and it must never write code. .agents/skills/grill-me/SKILL.md is a model. If /create-skill puts the folder somewhere else, move it to .agents/skills/.

    Prompt

    /create-skill A skill called ticket-to-spec. Given a Jira ticket file and the convention pages it references under docs/confluence, produce a mini-spec in specs/<ticket-key>.md with goal, assumptions, open questions, testable acceptance criteria, test cases and out of scope. It must flag conflicts between ticket and conventions and must never write code.

    Reference solution (look after you tried)
    ---
name: ticket-to-spec
description: Turns a Jira ticket plus linked Confluence conventions into a mini-spec with assumptions, open questions, acceptance criteria and test cases. Use when the user shares a ticket, or asks to refine, spec or plan a story before implementation.
---

1. Read the ticket and every document it references (docs/confluence/).
2. List conflicts and gaps between the ticket and the conventions.
3. Write specs/<ticket-key>.md with: Goal, Assumptions, Open questions,
   Acceptance criteria (each testable), Test cases (incl. edge cases), Out of scope.
4. Never write code. Ask the user to answer the open questions first.

## Gotchas
- Do not invent requirements. Mark every guess as an assumption.
- Keep the spec to one page.
  3. 3Run it on DWH-1028 min

    Start a new chat, invoke the skill from the slash menu and attach the ticket:

    Prompt

    /ticket-to-spec #file:tickets/DWH-102.md

    You should see: specs/DWH-102.md with open questions and at least one gap between ticket and pages: what counts towards the exposure (shipped orders only), which anchor for the rolling 30 days, whether customers with an approved exception are listed, which mart table and Power BI measure carry the result, and that the credit limit is not in the fact table yet. If the skill did not fire, sharpen its description (/skills shows what is registered).

    Answer two open questions in the chat and let the agent update the spec. You have the input for a clean implementation run without a line of code written. You do not implement DWH-102 today: the spec is the result of this part, so use the remaining minutes for the comparison, not for code. Compare your spec with your neighbor’s: whose description made the skill fire?

Wrap-up | 15 minutes (14:35 to 14:50)

Your working patterns

What would you do the same way on your team’s backend code tomorrow? Start from the examples, delete what does not fit, add your own, and decide where each pattern lives.

Working patternWhere it lives
How to decide where a pattern lives
  • Instructions: it is always true for this repo and short enough to be read on every request.
  • Skill: it is a procedure for some tasks, with steps, and it should load only when the task matches.
  • Habit: it is a way you work that no file can enforce. Write it down for the team anyway.
Questions for the discussion
  • Which step cost the most time?
  • Where did the agent surprise you?
  • What would you never delegate?
  • Test after (Part 1) or test first (Follow-up A): which would you choose for your team’s tickets, and why?
  • Which real tickets of your team fit this loop, and which do not?
Follow-up A | about 45 minutes

Test-driven development with a skill

Part 1 gave you a loop with a check script. Here the tests are the loop: the skill forces red before green.

  1. 1Read the skill8 min

    Open .agents/skills/test-driven-development/SKILL.md and writing-good-tests.md in your fork. The skill has one iron rule: no production code without a failing test first. Note down: the red, green, refactor cycle in your own words, and two excuses for skipping the test that the skill rejects.

  2. 2Read the ticket and branch off3 min

    Read tickets/DWH-103.md. The seed data contains three deliberately bad order rows: a duplicate, an amount of 0 and an unknown customer. Run the pipeline once so the stg tables exist, then create a branch:

    uv run dwh seed
uv run dwh run
git switch -c feature/DWH-103-order-quality

    The check reads stg.orders and stg.customers, so it is easy to test with a few hand-made rows. The repo has pytest, check with uv run pytest. Look at tests/conftest.py: the conn fixture gives you a clean database.

  3. 3Red: tests first10 min

    Start a new chat in Agent mode and call the skill explicitly:

    Prompt

    /test-driven-development Implement #file:tickets/DWH-103.md. Start with the tests for every acceptance criterion, using small hand-made rows in the conn fixture, and run them. Show me the failing output before you write any production code.

    You should see: Tests that fail for the right reason (the module quality.py does not exist yet), with the terminal output as proof. If the agent edits production code first: stop it, point to the iron rule and restart. That is the lesson, not a mistake of yours.

    git add -A
git commit -m "DWH-103 tests: order data quality check (red)"
  4. 4Green: the smallest change10 min

    Now ask for the minimum:

    Prompt

    Write the smallest production change that makes these tests pass. Do not add anything the tests do not require. Run the tests and show the output.

    You should see: All tests green, a short diff, no extras such as fixing the data or a new pipeline step (out of scope in the ticket). Read the diff against the ticket: is anything in it that no test demands?

    git add -A
git commit -m "DWH-103 check orders for duplicates, bad amounts and unknown customers (green)"
  5. 5Refactor and verify on real data7 min

    Ask for one improvement without changing behavior, run everything, and then point the check at the seeded data:

    Prompt

    Refactor for readability without changing behavior. Then run uv run pytest and show me the output. Finally call check_orders on the real seeded database and show me what it finds.

    You should see: The three bad rows from the seed: duplicate_order with 2 orders, non_positive_amount with 1, unknown_customer with 1.

    Then open a pull request for DWH-103 as in Part 1. The two commits (red, then green) are your proof of the method.

  6. 6Reflect5 min

    Write the two sentences into the PR description. Compare notes at the next session: where did the agent resist the rule, and what did you do?

Follow-up B | about 60 minutes

MCP: give the agent a new power

Do it on your own after the workshop. Connect one MCP server to az-copilot-backend-lab-2026-10, use it, and judge it like a dependency you would ship.

  1. 1Read how MCP servers are configured10 min

    MCP (Model Context Protocol) lets the agent call external tools: browsers, issue trackers, databases. In VS Code a server is a JSON entry under the key servers in .vscode/mcp.json (workspace) or a user configuration. Read the page MCP servers in VS Code and note: where does the config live, what happens on first start (trust dialog), and where do you switch single tools on and off?

  2. 2Wire one server15 min

    Pick one option and add it with MCP: Add Server in the Command Palette, or write the JSON yourself. Check it with MCP: List Servers. Use the Local session type.

    Option A: GitHub, the agent works your backlog

    Remote server, needs sign-in. VS Code asks you to trust it and to authenticate.

    {
  "servers": {
    "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp" }
  }
}
    Option B: Playwright, the agent drives a browser

    Server command: npx -y @playwright/mcp@latest (verify the package name in the current Playwright MCP docs). Needs Node.js 18 or newer. The first run downloads a browser. az-copilot-backend-lab-2026-10 has no web app, so you use it on documentation pages.

    {
  "servers": {
    "playwright": { "command": "npx", "args": ["-y", "@playwright/mcp@latest"] }
  }
}
    Option C: Jira and Confluence (only if your team allows the Atlassian Rovo MCP server)

    Ask your admin first. If available, this is the real version of the lab: ticket and policy page come from Jira and Confluence instead of files, and the ticket-to-spec skill from Part 2 works unchanged.

Help

Troubleshooting

First thing to try, always: paste the error into the chat and say what you expected.

uv run fails or wants to download Python

uv fetches Python 3.13 and pydantic on first use and needs network access to do so. Run uv sync once on a network that allows it, or ask a facilitator for a prepared fork.

“unable to open database file” or empty tables

Run uv run dwh seed once. The data folder data/ is created on demand and is git-ignored.

The check stays red

Run uv run scripts/lab_check.py and read which acceptance criterion fails. The check uses its own demo history, so a live uv run dwh run does not influence it.

The status shows a different run than expected

The report shows the latest run by run id. After uv run dwh run that is your live run, not the demo history from 2026-10-06. To see the demo run again, delete the folder data/ and run uv run dwh seed.

I want to see the data

uv run dwh peek schema.table shows the first rows of any table, for example src.orders, core.orders or ctl.dwh_control. Add --rows 20 for more.

The pipeline reports ORA errors that are not mine

Only --inject-failure STEP raises a simulated ORA-00942. Without that flag, a real failure means a bug in a SQL file: paste the error and the SQL file into the chat.

I cannot find Plan mode or the model picker

Both live in the chat input: the agent picker (Ask, Agent, Plan) and the model picker. Make sure the session target is Local.

My instructions or skill are not picked up

Check the References under the answer. For instructions, the setting chat.useAgentsMdFile must be on for the Local agent. For skills, the folder name must equal name in the frontmatter, and /skills shows what is registered. For details run Developer: Open Agent Debug Logs from the Command Palette.

“Reopen in Container” fails or hangs

Docker must be running and have network access for the first build. Check the Dev Containers output (Command Palette: Dev Containers: Show Container Log). Without Docker use uv locally.

The agent wants to run a terminal command

That is the default permission level. Read the command, then click Allow. Never allow commands you do not understand.

Copilot Code Review button is missing

Whole-change review needs a paid plan. Use the selection review (right-click, Generate Code, Review) or the fallback prompt in the review step.

tickets/DWH-101.md

DWH-101 | Make the pipeline status readable for the whole team
Type: Story | Priority: Medium | Component: Monitoring
Reporter: BI Team Lead | Status: Ready for Dev

Description
As a member of the BI team I want to see the status of the last pipeline run without asking
a data engineer, so that I know every morning whether the reports can be trusted.
Today `uv run dwh status` prints a raw dump of the log table.

Acceptance criteria
1. The first line reads: "Pipeline run <date>: <n> of <total> steps OK, <f> failed, <s> skipped, <l> late"
   (example: "Pipeline run 2026-10-06: 7 of 9 steps OK, 1 failed, 1 skipped, 1 late").
2. Failed steps are listed first, with step name, layer and Oracle error.
3. A skipped step names the failed step it depends on and is not shown as FAILED.
4. A late step is flagged "LATE" with the minutes after 06:00, as defined in docs/confluence/pipeline-operations.md.
5. The output is stable: the same log gives the same text.
6. scripts/lab_check.py passes.

Out of scope
Sending the status by mail, a web page, new columns in ctl.dwh_control.

tickets/DWH-102.md

DWH-102 | Check customers for credit limit breaches
Type: Story | Priority: Medium | Component: Sales Reporting
Reporter: Head of Credit Management | Status: Needs refinement

Description
Sales orders should be checked against the credit limits of our customers across all product lines,
so Credit Management can see problem customers before the Monday review. Result should show up

DWH-103 | Check order data for typical errors before the load
Type: Story | Priority: Medium | Component: Data Quality
Reporter: BI Team Lead | Status: Ready for Dev

Description
Bad rows in the source reach the reports unnoticed: the same order twice, orders without an amount,
orders of customers we do not know. I want a check that finds them in stg.orders, so the team can
see them before the Monday review.

Acceptance criteria
1. check_orders(conn) in src/dwhpulse/quality.py returns a list of issues. Each issue is a frozen pydantic model with: rule, count, order_ids (at most the first 5, ascending).
2. Rule "duplicate_order": the same PRODUCT_ID, CUSTOMER_ID and ORDERED_AT appear more than once. All rows of such a group count.
3. Rule "non_positive_amount": AMOUNT_EUR is 0 or negative.
4. Rule "unknown_customer": CUSTOMER_ID does not exist in stg.customers.
5. A rule without findings is not part of the result. Clean data gives an empty list.
6. The check only reads, it never changes a table.
7. Unit tests cover every rule, the clean case and the "at most 5 ids" limit.

Out of scope
Fixing the data, mails, a pipeline step, new tables.

# Sales credit policy (simulated Confluence page)

## Why
Sales must not ship to customers who exceed their credit exposure, whatever product line or
channel the orders come through.

## Rules
- The shipped order value of a customer in any rolling 30 days must not exceed the customer's
  credit limit (CREDIT_LIMIT_EUR), summed across all product lines and sales channels.
- Customers with a credit block never appear in reporting.
- A sales manager can request an exception for one customer, approved by Credit Management.
- Orders of discontinued products are not part of the check.

## Reporting
- The Power BI report "Sales Credit Monitor" shows the check per week.
- Credit Management reviews the report every Monday.
- Customers above the limit are listed with their orders, never with more than the customer id and segment.

# Pipeline operations (simulated Confluence page)

## Layers
- SRC: simulated source system. Read only.
- STG: raw copy plus load timestamp. No business logic.
- CORE: cleaned and conformed data. Credit-blocked customers and discontinued products stop here.
- MART: tables for reporting, one per Power BI table.

## Run and status
- The pipeline starts at 05:00. Every step writes one row into ctl.dwh_control.
- A step that fails is logged as FAILED with the Oracle error. Steps that depend on it are SKIPPED.
- The status must be readable for people who are not data engineers, and available by 06:00.
- A successful step that finishes after 06:00:00 counts as late. A step that finishes at exactly 06:00:00 is on time.
- Lateness is reported in started minutes: a step that finishes at 06:00:30 is 1 min late.
- Failed and skipped steps are reported as FAILED or SKIPPED, never as late.

## Naming
- Step names: layer prefix plus table, for example `core_orders`.
- SQL files are numbered per layer and run in the order of pipeline.py.
- No SELECT * in SQL files. Explicit column lists only.

## Errors
- Bad source rows (duplicates, amounts of 0 or less, unknown customers) are reported before the Monday review.
- A rerun of any step must give the same result (idempotent).

<!-- Adapted from github.com/mattpocock/skills (MIT). -->

Interview the user until you reach a shared understanding. Map the topic as a design tree:
every decision branches into the decisions that hang off it.

Work in rounds. The frontier is every decision whose prerequisites are already settled.
Ask the whole frontier in one round: number each question and give your recommended answer.
Then wait for the answers before the next round.

Format of a round:

Q1 - <question title>: <question, with options if useful>
Recommended: <your answer>

Rules:
- Facts are your job, not the user's. Look them up in the repo with your read and search tools
  instead of asking.
- Decisions are the user's. Put each to them and wait.
- Done when the frontier is empty: every branch visited, nothing silently assumed.
- Do not act on the result until the user confirms the shared understanding.

Note: The Confluence pages and all tickets are invented for this lab. Replace them with real artifacts of your team when you repeat the exercise on your own code.
